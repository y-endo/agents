# impl-explainer

目的: エンジニアがその変更を**自分の言葉で**説明できるようになること。「AIの要約を読む」ことではなく、「自分の仮説をコード上の事実で検証し、誰も決めていないことと、テストが証明していないことを把握する」ことです。

Claude Code と Codex で動作します。「ユーザーに尋ねる」とは、質問用ツールがあればそれを使い、なければチャットで尋ねて返答を待つことを指します。
レポートは**日本語**で書きます（テンプレート、見出し、ラベルは日本語）。ユーザーとの会話はユーザーの言語で行います。

## 譲れないルール

1. **仮説が先。** Phase 0 の回答が届くまで、コードについての説明・要約・意見を一切述べない。
2. **主張には根拠を付ける。** 挙動・設計に関する主張には `[[path:line]]` を付け、引用した行が実際にその主張を裏付けていること。コードの抜粋は、書き写さず snippets 構文で実ファイルから取り込む。
3. **確度ラベル。** `【確認済み】`（読んだ、または実行した）、`【推測】`（意図や理由を推測した）、`【未確認】`（未検証、または検証できない）。「なぜそう作られたか」は、記録（コミットメッセージ、コメント、チケット、エージェントへの指示）がない限り `【推測】`。
4. **テストが通っても、証明されるのはそのテストが調べている範囲だけ。** コマンドと出力を証拠にそのまま記録し、それらが証明していないことを明記する。
5. **自分の要約も疑う。** Phase 5 は新しいコンテキストでの検証。
6. **水増ししない。** 項目が空なら1行で `該当なし`。指摘、質問、図で水増ししない。
7. **作業ツリーを絶対に変更しない**（`git checkout` / `stash` / `reset`、ファイルの巻き戻し）。ユーザーの未コミットの作業が失われるため。

## 役割

- **オーケストレーター** = ユーザーが依頼したモデル（あなた）。ヒアリング、理解、すべての判断、レビュー、引き渡しを担当する。品質に責任を持つ。
- **ワーカー** = 作業用モデル（workhorse model）。あなたのブリーフ（brief）をMarkdownページに変換し、ビルドを実行する。新しい判断はしない。
- **検証者（Verifier）** = 新しいコンテキストのエージェント。完成したレポートだけを検証する。

モデルの選び方、起動方法、レビューのチェックリスト: `references/delegation.md`（Phase 3 の前に読むこと）。

## フロー

```
P0 hypothesis interview → P1 scaffold → P2 read & judge          (orchestrator)
P3 brief → worker writes pages & builds                          (worker)
P4 review, ≤2 fix rounds → P5 fresh-context verification → P6 hand-off   (orchestrator)
```

スクリプトはこのファイルと同じ場所の `scripts/` にあります（以下 `<skill>`）。Python 3.10 以上の標準ライブラリのみ。`python -X utf8` で実行します。`build.py` は固定バージョンの MkDocs を自分で用意します（`uv` があれば使い、なければ venv。初回はインターネット接続が必要）。スクリプトのメッセージには、エラー時にどうすればよいかが書かれています。

## Phase 0: 仮説ヒアリング（必ず最初に）

`references/hypothesis-interview.md` に従い、6つの質問を1通のメッセージで尋ねます（「わからない」も有効な回答）。範囲を提案するときに見せるのは、ブランチ名、ベース、コミット数、ファイル名だけ（`git rev-list --count <base>..HEAD`, `git diff --name-only <base>...HEAD`）。**コミットの件名は絶対に見せない**（AI自身の要約であり、仮説を引きずってしまう）。

## Phase 1: 土台の作成と事実の収集

```bash
python -X utf8 <skill>/scripts/new_report.py --repo <repo_root> --slug <name> --hypothesis <answers_file> [--base <ref>] [--head <ref>] [--uncommitted]
```

- `<answers_file>`: ユーザーの Phase 0 の返答を、リポジトリの外か `<repo>/.impl-explainer/` 配下（差分の対象外）のファイルに原文のまま保存したもの。`validate.py` が、レポートに原文のまま貼られているかを確認する。ユーザーが回答を断った場合、または質問3〜5がすべて「わからない／なし」だった場合に限り、代わりに `--no-hypothesis` を使う。
- デフォルトのベース: main/master とのマージベース（なければ `HEAD~1`）。`--uncommitted` は作業ツリーの変更を対象にする（`--base` を指定した場合は `base..HEAD` のコミットも含む）。
- `<repo>/.impl-explainer/<date>-<slug>/`（git の管理対象外）を作成し、コミット／変更ファイル／差分統計を機械的に `docs/evidence.md` に書き込む。同じ slug を再度使うには `--force` が必要（古いレポートは `<dir>.bak-<日時>` として残る）。コードを変更した後は新しい slug を使うほうがよい。
- 停止したり警告を出したりした場合（対象ファイルに未コミットの編集がある、差分が大きい など）は、ユーザーに伝え、その選択に従う。

## Phase 2: 読んで判断する（オーケストレーター）

差分を**すべて**読み、さらに呼び出し元・呼び出し先も、挙動を説明できるようになるまで読みます。実行してよいのは安全で短時間の確認（テスト、ビルド）だけで、外部サービスや本番設定への書き込みは決してしません。使い捨ての確認用スクリプトはリポジトリの外に置きます。次の各項目を、それぞれ `[[path:line]]` を付けて判断します:

- 入口（API/UI/CLI/ジョブ）から出口（DB/外部/レスポンス）までの主な経路、分岐、失敗経路。状態が変わる場所（DB、ファイル、メモリ上の値、外部呼び出し）と、その**後**で失敗しうること（「失敗時は何も変わらない」が成り立つのは、状態変更より前の失敗だけ）。
- 主張ごとの仮説の判定: `一致` / `部分一致` / `相違` / `判断不可`。
- 怪しいコード（握りつぶされた例外、意味のないリトライ、デッドコード、共有状態、時刻／金額／文字コード、セキュリティ）: 重要度 `高`/`中`/`低`、確認方法。スタイルの好みは対象外。
- 差分の外への影響: この変更によって、挙動や意味が変わる未変更のコード（変更された関数の呼び出し元、変更されたデータ・設定・既定値・例外・戻り値の読み手、共有状態、変更されたファイル内の未変更の行）。明示的に探し、探し方（コマンド）を記録する。
- 示された要件に対する過剰実装、より単純な代替案、単純にすると失うもの。
- 要件にない挙動と未対応の項目（`既定値` / `要件の読み替え` / `要件にない追加` / `未対応`）。記録がない限り、誰が決めたか、意図的に除外されたかを主張しない。
- 各テストが証明していることと、証明していないこと。
- FAQ（5〜8件）とクイズ（5〜7件）。`references/faq-and-quiz.md` に従う。

## Phase 3: ブリーフの作成と委任

`assets/brief-template.md` を `<report_dir>/brief.md` にコピーし、Phase 2 のすべての判断とその根拠を記入します。ブリーフはワーカーにとって唯一の情報源です。`references/delegation.md` に従い、`references/worker-prompt.md` を使ってワーカーを起動します。ワーカーを起動できない場合、またはあなた自身が作業用クラスのモデルである場合は、同じ参照資料（`references/report-structure.md`、`references/diagram-guide.md`、`references/faq-and-quiz.md`）に従って自分でページを書きます。

## Phase 4: オーケストレーターによるレビュー

`references/delegation.md` の「Review」に従います。重要な主張については、引用された行を自分で開いて確認します。ワーカーの要約を証拠として受け入れてはいけません。修正依頼は1通のメッセージにまとめて送り、最大2ラウンド。その後に残る小さな問題は自分で直します。

## Phase 5: 新しいコンテキストでの検証

リポジトリとレポートのパスだけを渡し（あなたの結論は渡さない）、`references/verifier-prompt.md` を使って検証者を起動します。採用するのは、事実の誤り、重要な挙動の欠落、根拠のない断言だけ。1回限りで、やり取りの往復はしません。採用する前に、指摘を自分で再確認し（該当行を読む・実行する）、そのコマンドと出力を `evidence.md` の「実行した確認」に記録します。検証者の申告だけで【確認済み】にしてはいけません。先に `brief.md` を直し、それから作業モデル（または自分）に反映させます。新しいコンテキストを用意できない場合は1回だけ自己チェックしてもよいが、evidence に `未実施（自己チェックのみ）` と記録し、Phase 6 でもその旨を伝えます。

## Phase 6: 引き渡し

`python -X utf8 <skill>/scripts/build.py <report_dir>`（検証＋ビルド）を最後にもう一度実行します。ERROR は0であること。ブラウザを操作できるなら、図のあるページ（index/flow/design）のスクリーンショットを撮り、Mermaid が描画されていることを確認します（Material は閉じた shadow DOM に描画するため、JS では確認できません）。ブラウザで `file://` を開けない場合は `python -m http.server 8000 --directory <report_dir>/site` で配信して開きます。ユーザーには次の内容を簡潔に伝えます:

1. `site/index.html` の絶対パス（直接開く。図の表示にはインターネット接続が必要）。
2. 仮説の結果（件数と、最も大きな相違）。
3. 要注意トップ3（各1行、参照付き）。
4. 「クイズに答えられない場合は、その問題の参照先を読み直してください」。
5. 未実施・未検証のこと（検証、図の描画、未実行のテスト）。

レポートをチャットに貼り付けてはいけません。
