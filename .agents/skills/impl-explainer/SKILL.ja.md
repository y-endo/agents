# impl-explainer

エンジニアの事前理解をコードの根拠と照合し、変更内容を自分の言葉で説明できるようにする。
判断の理由が記録されていない箇所と、テストで確認できていない挙動を明らかにする。

Claude CodeとCodexで使用する。
「ユーザーに尋ねる」とは、質問用ツールがあればそれを使い、なければチャットで尋ねて回答を待つことを指す。
レポートの本文、テンプレート、見出し、ラベルは日本語にする。
ユーザーとの会話には、ユーザーの言語を使う。

## 必須ルール

1. **仮説を先に聞く**：Phase 0の回答を受け取るまで、コードの説明、要約、意見を述べない。
2. **主張に根拠を付ける**：挙動や設計の主張には `[[path:line]]` を付け、その行が主張を裏付けるか確認する。コードは書き写さず、snippets構文で実ファイルから取り込む。
3. **確度を示す**：読んだ内容や実行結果には `【確認済み】`、意図や理由の推定には `【推測】`、未検証の内容には `【未確認】` を付ける。設計理由は、コミットメッセージ、コメント、チケット、指示文などの記録がない限り `【推測】` とする。
4. **テストの確認範囲を区別する**：コマンドと出力を原文のまま記録し、そのテストでは確認できないことも示す。
5. **自分の要約も検証する**：Phase 5では、会話履歴を引き継がないエージェントが検証する。
6. **項目を水増ししない**：対象がなければ `該当なし` と1行で記載する。件数を満たすためだけに指摘、質問、図を追加しない。
7. **対象リポジトリを保全する**：ソースの編集、ブランチの切り替え、stash、reset、作業の巻き戻しを行わない。レポートとローカルキャッシュは `.impl-explainer/` 配下に作成する。許可された環境では、ビルド環境にユーザーキャッシュも使える。

## 役割

- **統括担当（orchestrator）**：ユーザーから依頼を受けたモデル。聞き取り、コードの理解、判断、レビュー、引き渡しを担当し、品質に責任を持つ。
- **執筆担当（worker）**：統括担当の作業指示書（brief）をMarkdownページにまとめ、ビルドする作業用モデル。新たな判断は行わない。
- **検証担当（verifier）**：会話履歴を引き継がず、完成したレポートを検証するエージェント。

モデルの選択、起動方法、レビュー項目は `references/delegation.md` に従う。
Phase 3の前に読む。

## 作業の流れ

```text
P0 仮説の聞き取り → P1 ひな形の作成 → P2 調査と判断       （統括担当）
P3 作業指示書に基づく執筆とビルド                          （執筆担当）
P4 レビューと最大2回の修正 → P5 独立した検証 → P6 引き渡し  （統括担当）
```

## 実行環境と文体

スクリプトは、このファイルと同じディレクトリの `scripts/` にある。
以下ではスキルのディレクトリを `<skill>` と表す。
開始前にGitとPythonを確認する。
Python 3.10以上が必要になる。
macOSとLinuxでは `python3 --version`、Windowsでは `py -3 --version` または `python --version` で確認する。
以後の実行では、確認したPythonを一貫して使う。
以下の例は `python3` を使うため、必要に応じて `py -3` または確認済みの実行ファイルに置き換える。
パスには空白が含まれることがあるため、例のプレースホルダーも含めて引用符で囲む。

スクリプト自体はPythonの標準ライブラリだけを使う。
`build.py` は `assets/requirements.lock` の依存パッケージを、uvがあればuvで、なければvenvで準備する。
初回のビルドにはインターネット接続が必要になる。
サンドボックスとネットワークの権限に従い、準備できなければ制約を報告する。
配布するスキルのディレクトリに `__pycache__` を残さないよう、`-B` を付ける。

日本語の手順書は常体、レポートは敬体で書く。
一文ごとに改行し、一つの段落で一つの話題を扱う。
なじみのない用語は初出で説明する。
装飾的な強調、内容のない総括、ダッシュによる挿入、中黒による語の並列を新しい文章に使わない。
不確実性、回答の原文、コード、ログ、テンプレートの固定見出しは保つ。
レポート固有の規則は [references/report-structure.md](references/report-structure.md) にまとめており、別の文章作成スキルのインストールは不要である。

## Phase 0: 事前の仮説を聞く

`references/hypothesis-interview.md` に従い、6つの質問を1通のメッセージで尋ねる。
「わからない」も回答として受け付ける。
範囲を提案するときは、ブランチ名、比較元、コミット数、ファイル名だけを示す。
確認には `git rev-list --count <base>..HEAD` と `git diff --name-only <base>...HEAD` を使う。
コミットの件名は示さない。
AIが書いた要約が、ユーザーの仮説に影響するためである。

## Phase 1: ひな形の作成と事実の収集

```bash
python3 -B -X utf8 "<skill>/scripts/new_report.py" --repo "<repo_root>" --slug <name> --hypothesis "<answers_file>" [--base <ref>] [--head <ref>] [--uncommitted]
```

- `<answers_file>`には、Phase 0の回答を原文のまま保存したファイルを渡す。保存先はリポジトリの外、または差分から除外される `<repo>/.impl-explainer/` 配下とする。`validate.py` が原文との一致を確認する。回答を断った場合、または質問3〜5の回答がすべて「わからない」「なし」の場合に限り、`--no-hypothesis` を使う。
- 比較元の既定値はmainまたはmasterとのマージベースで、見つからなければ `HEAD~1` を使う。`--uncommitted` は作業ツリーの変更を対象とし、`--base` も指定した場合は `base..HEAD` のコミットを含める。
- Gitの管理対象外となる `<repo>/.impl-explainer/<date>-<slug>/` を作成し、コミット、変更ファイル、差分統計を `docs/evidence.md` に出力する。同じslugを再利用する場合は `--force` が必要で、以前のレポートを `<dir>.bak-<日時>` に保管する。コードを変更した後は、新しいslugを使うことを優先する。
- 対象ファイルの未コミット変更や大きな差分によって停止や警告が出た場合は、内容をユーザーに伝え、その選択に従う。

## Phase 2: コードを調べて判断する

統括担当が差分をすべて読み、挙動を説明できる範囲まで呼び出し元と呼び出し先を調べる。
実行する確認は、安全で短時間に終わるテストやビルドに限る。
外部サービスや本番設定への書き込みは行わない。
使い捨ての確認用スクリプトはリポジトリの外に置く。
次の項目を判断し、それぞれに `[[path:line]]` の根拠を付ける。

- API、UI、CLI、ジョブなどの入口から、DB、外部サービス、レスポンスなどの出口までの処理、分岐、失敗時の挙動。DB、ファイル、メモリ、外部呼び出しで状態が変わる位置と、その後に失敗しうる処理を確認する。「失敗しても状態は変わらない」と説明できるのは、状態変更より前の失敗に限る。
- 仮説の各主張に対する `一致`、`部分一致`、`相違`、`判断不可` の判定。
- 例外の握りつぶし、不要な再試行、使われないコード、共有状態、時刻、金額、文字コード、セキュリティなどの懸念。重要度を `高`、`中`、`低` で示し、確認方法を記載する。文体や書き方の好みは指摘しない。
- 差分に含まれないコードへの影響。変更した関数の呼び出し元、データや設定、既定値、例外、戻り値の利用箇所、共有状態、変更ファイル内の未変更行を明示的に探し、使ったコマンドを記録する。
- 要件に照らした過剰実装、より単純な代替案、その案で失うもの。
- 要件にない挙動と未対応事項。`既定値`、`要件の読み替え`、`要件にない追加`、`未対応` に分類する。記録なしに、判断した人物や除外の意図を断定しない。
- 各テストで確認できることと、確認できないこと。
- `references/faq-and-quiz.md` に従った想定質問5〜8件と理解度クイズ5〜7件。

## Phase 3: 作業指示書の作成と委任

`assets/brief-template.md` を `<report_dir>/brief.md` にコピーし、Phase 2の判断と根拠を記入する。
執筆担当は、この作業指示書を判断の基準にする。
`references/delegation.md` に従い、`references/worker-prompt.md` を使って執筆担当を起動する。
起動できない場合、または統括担当が作業用クラスのモデルである場合は、自分で執筆する。
その場合も `references/report-structure.md`、`references/diagram-guide.md`、`references/faq-and-quiz.md` に従う。

## Phase 4: 統括担当によるレビュー

`references/delegation.md` の「Review」に従う。
重要な主張の引用行を自分で開き、内容を確かめる。
執筆担当の要約だけを証拠として扱わない。
修正依頼は1通にまとめ、修正と再確認は最大2回とする。
その後に残った軽微な問題は、自分で直す。

## Phase 5: 会話履歴を引き継がない検証

`references/verifier-prompt.md` を使い、リポジトリとレポートのパスを渡して検証担当を起動する。
統括担当の結論は渡さない。
事実の誤り、重要な挙動の欠落、根拠のない断定だけを修正対象とする。
検証は1回とし、指摘の応酬は行わない。

指摘を採用する前に、自分で該当行を読むか実行して確かめる。
コマンドと出力を `evidence.md` の「実行した確認」に記録する。
検証担当の申告だけで `【確認済み】` にしない。
先に `brief.md` を直し、その後に執筆担当または自分がページへ反映する。
独立した検証環境を用意できない場合は、一度だけ自己チェックしてよい。
その場合は `未実施（自己チェックのみ）` と記録し、Phase 6でも伝える。

## Phase 6: 引き渡し

最後に `python3 -B -X utf8 "<skill>/scripts/build.py" "<report_dir>"` を実行し、検証とビルドを通す。
ERRORが0であることを確認する。
ブラウザを操作できる場合は、図のあるindex、flow、designの各ページを開き、スクリーンショットでMermaidの描画を確認する。
ビルドの成功だけでは、図が描画されることまでは確認できない。
`file://` を開けない場合は、`python3 -m http.server 8000 --bind 127.0.0.1 --directory "<report_dir>/site"` でローカル配信し、確認後にサーバーを停止する。
ユーザーには次を簡潔に伝える。

1. `site/index.html` の絶対パス。ファイルを直接開けることと、図の表示にはインターネット接続が必要なこと。
2. 仮説の判定件数と、最も大きな相違。
3. 注意点を最大3件。それぞれ1行で根拠を添える。
4. クイズに答えられない場合は、その問題の参照先を読み直すこと。
5. 独立した検証、図の描画、テストなど、未実施または未確認の事項。

レポートの全文はチャットに貼り付けない。
