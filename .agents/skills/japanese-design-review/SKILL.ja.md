# 日本語Webデザインをレビューする

依頼された最小範囲のWeb成果物をレビューし、非デザイナーがリリースまたは修正を判断できる形でリスクを示す。
プロジェクト、そのユーザー、実際の日本語コンテンツを最優先の証拠として扱う。

## 責務の境界を守る

- プロジェクトの調査やコマンド実行より前に、適用される統治文書をすべて読む。
- ユーザーが実装を別途依頼しない限り、レビュー依頼をread-onlyとして扱う。
- `design-spec`、`DESIGN.md`、Figma、デザインシステムがなくても作業する。
- デザイン契約や承認済み参照が存在する場合は、本Skillの依存先ではなくプロジェクトの証拠として使う。
- 新しいデザイン方向の探索と`DESIGN.md`作成は、利用可能な場合に`design-spec`へ振り分ける。
- Figmaを根拠とする実装または再同期は、利用可能な場合に`figma-codegen`へ振り分ける。
- 明示許可なく非公開のコード、スクリーンショット、アセット、ユーザーデータを外部サービスへ送らない。
- 専門家によるデザイン承認、ユーザビリティテストの証拠、アクセシビリティ適合認証を主張しない。

## 必要な詳細だけを読む

- 画面、ページ、フロー、コンポーネント、リリースを判定する前に[review-criteria.md](references/review-criteria.md)を読む。
- 日本語デザインの一般則を適用するか、外部情報を引用する前に[source-cards.md](references/source-cards.md)を読む。
- 日本語の文言、改行、レスポンシブな文字組み、UI状態をテストする前に[content-test-cases.md](references/content-test-cases.md)を読む。
- 依頼範囲が曖昧な場合、証拠が不足する場合、単一コンポーネントだけをレビューする場合は[conversation-examples.md](references/conversation-examples.md)を読む。

## 証拠の優先順位に従う

判断が競合する場合は、次の順序で解決する。

1. 確認済みのプロジェクト固有ユーザー、タスク、実コンテンツ、制約、対応環境
2. 適用可能なアクセシビリティ標準と日本語組版要件
3. 確認済みのブランド規則、デザイン契約、コンポーネント、トークン
4. 理由、例外、検証方法を持つ適用範囲付きsource card
5. 注釈付きの国内事例、受賞事例、ギャラリー、トレンド

国内事例、受賞、ギャラリー掲載、書籍を、ユーザビリティ、コンバージョン、プロジェクト適合性の証明として扱わない。
プロジェクト固有の判断を、汎用デザインシステムの初期値で置き換えない。

## レビュー手順に従う

### 1. 範囲を確定する

レビュー対象のページ、画面、フロー、コンポーネント、差分を特定する。
ユーザーが部分的な批評、リリース判断、証拠が限られたベースラインレビューのどれを必要としているかを判断する。
最小限の代表面と、それを直接規定するコンテンツ、スタイル、コンポーネント、ルート、テストを調べる。

次を記録または発見する。

- 主要ユーザーとタスク
- ページまたは機能の目的
- 実際の日本語コンテンツ
- 対応viewport範囲と関連するdevice class
- 必要な通常、hover、focus、selected、disabled、loading、empty、error、success状態
- ブランド、実装、パフォーマンス、アクセシビリティの制約
- 利用可能なrender、DOM、読み上げ順序、focus順序、interactionの証拠

ローカルで確認できない重要情報だけを質問する。
有用な指摘が可能な場合は、証拠を限定した狭いレビューまで止めない。

### 2. 証拠と仮定を分ける

実際に調査した成果物を列挙する。
推定したプロジェクト情報は仮定として示し、レビューへの影響を説明する。
主張に必要な証拠を取得できない場合は`Not checked`を使う。
承認済み範囲の外側にあるgateだけを`Not applicable`とする。
`Not checked`を`Pass`へ変換しない。
gateの適用可否は、証拠の有無を考慮する前に、対象成果物の性質と承認済み範囲から決める。

視覚的な主張では、環境が許す限り対象viewportの最新renderを確認する。
コードだけでは、表示上の改行、文字切れ、階層、focus表示、responsive順序を証明できない。
部分的なcodeやCSSに指定が見つからないことを、表示、状態、挙動が存在しない証拠として扱わない。
対象成果物の完全性を確認できない場合は、`Fail`ではなく`Not checked`とする。

### 3. 代表的な日本語コンテンツをテストする

製品の実際の文言を最初に使う。
[content-test-cases.md](references/content-test-cases.md)から、対象に関係する境界値だけを追加する。
対応する狭い幅と広い幅、適用可能な場合は200%までのbrowser zoom、環境が対応する場合はfontまたはtext sizeの変更を確認する。

一つのスクリーンショットだけに手動改行を最適化しない。
意味を保ち、その改行が現れる対応条件のすべてで成立する場合だけ、意図的な改行を許容する。

### 4. ユーザーへの影響順にレビューする

[review-criteria.md](references/review-criteria.md)を次の順序で適用する。

1. ユーザータスクと情報設計
2. 日本語の文章と文字組み
3. 視覚階層と注意の順序
4. レスポンシブとUI状態
5. 操作性とアクセシビリティ
6. ブランド適合性とプロジェクト固有の独自性

想定したF型やZ型ではなく、ユーザーのタスクから注意の順序を評価する。
desktopとmobileを別々に確認する。
証拠を取得できる場合は、視覚順序とDOM、読み上げ、focus順序を比較する。

### 5. Gateと指摘を判定する

適用するHard Gateを`Pass`、`Fail`、`Not checked`、`Not applicable`のいずれかで評価する。
`Fail`が一つでもあれば、リリース可能とは判定しない。
重要な`Not checked`があれば部分的な結果とし、完全なリリース判定を出さない。

指摘を次の重大度順で報告する。

- `Blocker`：主要タスク、理解、操作、責任あるリリース判断を妨げる
- `Major`：影響するユーザーへ大きな負荷、誤操作リスク、誤解を生じさせる
- `Minor`：局所的な摩擦、不整合、可読性低下を生じさせる
- `Suggestion`：要件違反を示さず、根拠のある改善案を提示する

数値スコアを付けない。
根拠なく精密に見える数値は、較正済みのユーザー証拠や製品証拠を代替できない。

### 6. 修正に使える形で報告する

次の順序で報告する。

1. レビュー範囲と使用した証拠
2. Hard Gate一覧
3. 重大度順の指摘
4. 未確認領域と残存リスク
5. 再確認手順

各指摘に次を含める。

- 指摘IDと重大度
- 正確な対象箇所
- 解釈と分けた観察事実
- 影響するユーザーとタスク
- プロジェクト要件またはsource card ID
- 無断実装を伴わない修正方針
- 検証方法
- 確信度

称賛より先にBlockerとMajorを示す。
修正時に維持すべき判断へ影響する場合だけ、機能している点を記載する。
ユーザーの言語を使い、日本語プロジェクトでは日本語を既定とする。

## 定型的なレビューを避ける

グラデーション、glass表現、大きな角丸card、bento grid、抽象的な3D object、中央寄せhero、glow、particle、illustrationを、生成物で頻出するという理由だけで否定しない。
プロジェクト固有の理由がない、階層を不明瞭にする、タスクを妨げる、ブランドと衝突する、参照元を識別できる組合せを模倣する場合だけ指摘する。

固定的な「日本風の見た目」を強制しない。
日本語圏への適合性は、必須の視覚様式ではなく、コンテンツ、組版、ユーザーの期待、利用文脈から判断する。
