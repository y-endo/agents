# コミットメッセージを生成する

ユーザーから与えられた情報と、確認済みのstage差分からコミットメッセージを1件生成する。

## コミットメッセージのルール

リポジトリ固有のコミットルールがある場合は、そのルールに従う。
ルールがない場合は、次の形式を使う。

```text
[<type>] <ticket-id> <subject>

<body>
```

- リポジトリでtypeが定義されていない場合は、一般的な`feat`、`fix`、`docs`、`refactor`、`test`、`perf`、`build`、`ci`、`style`、`chore`、`revert`を使う。
- stage差分を最も適切に表すtypeを選ぶ。
- ユーザーが確認したチケットIDを、大文字小文字と記号を含めてそのまま使う。
- subjectとbodyは日本語で記載する。type、チケットID、リポジトリ指定の構文は変更しない。
- subjectは可能な限り50文字以内とし、stageされた変更を要約する。
- bodyには重要な変更内容を箇条書きで記載する。
- それ以外の書式は、リポジトリで定着している文体に従う。

例:

```text
[perf] <TICKET-1234> ユーザー一覧取得のパフォーマンス改善

- N+1クエリをeager loadingで解消
- 変更後のAPIレスポンスに一覧表示を対応
```

## 作業手順

1. リポジトリの指示とコミット規約を読む。
2. `git status --short`、staged、unstaged、untrackedの変更を確認する。
3. すでにstageされているファイル、stage候補、対象外候補を報告する。
4. 正確なチケットIDと対象ファイルをユーザーに確認する。
5. 承認されたファイルがstageされていない場合は、そのパスだけを指定して`git add -- <exact-paths>`を実行する。
6. `git status --short`、`git diff --cached --stat`、`git diff --cached`を再確認する。
7. 確認済みのstage差分からメッセージを生成する。
8. 正確なstage対象と最終メッセージを提示し、その組み合わせでコミットしてよいかを別個に確認する。
9. 明示的な回答を得るまで停止する。ユーザーがそのstage差分とメッセージを明確に許可した場合だけ`git commit`を実行する。
10. コミットが成功したら、`git status --short`と`git log -1 --oneline`で結果を確認する。

パスは使用中のshellに合わせてクオートする。
`git add .`、`git add -A`、glob、広いディレクトリ、`git add --force`を使わない。
対象外のファイルがすでにstageされている場合は、自動的にunstageせず、矛盾を報告して停止する。
チケットIDと対象ファイルの両方をユーザーが確認するまで、最終的なメッセージを生成しない。

## コミット実行の許可

ファイルをstageする許可、メッセージの作成依頼、作業を続ける一般的な指示、最終的なstage差分とメッセージを提示する前に与えられた許可は、コミット実行の許可として扱わない。
コミット実行の許可を推測しない。
メッセージを提示した手順内では`git commit`を実行しない。
許可後にindexまたはメッセージが変わった場合は、変更後のstage対象とメッセージを提示し、明示許可を再度得る。
ユーザーが個別に求めない限り、`--amend`、`--no-verify`、`--allow-empty`を使わない。
コミットフックが失敗した場合は、失敗を報告し、回避しない。

## 出力

次を簡潔に報告する。

- 確認済みのチケットID
- stage対象に含めたファイル
- stage対象から除外したファイル
- このスキルがstageしたファイル。該当しない場合は`なし`
- コピー可能なコードブロックに入れたコミットメッセージ案
- コミット実行の明示許可が必要かどうか
- 許可後にコミットが成功した場合はコミットハッシュ。実行していない場合はその旨

明示承認された`git add -- <exact-paths>`と、提示した正確なstage差分およびメッセージに対して明示許可を得たコミット以外では、ファイル、ブランチ、refs、indexを変更しない。
