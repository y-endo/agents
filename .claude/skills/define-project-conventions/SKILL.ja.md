# プロジェクト規約策定

汎用テンプレートを押し付けたり既存慣行を無断で書き換えたりせず、プロジェクトに適した規約の契約を作成する。

## プロジェクトの権限を守る

- プロジェクトのコマンド実行や内容調査の前に、ルートと下位の`AGENTS.md`、`CLAUDE.md`、コントリビューションガイド、リポジトリ方針など、適用されるすべての統治文書を特定して従う。
- ユーザーがファイル変更を明示的に許可するまで、作業を助言として扱う。監査、提案、承認、適用、検証を分ける。
- 事実確認に必要な最小限のmanifest、lockfile、runtime固定設定、source、test、tool設定、CI、文書を読む。
- 秘密情報、依存物の内容、生成物、無関係なproduct codeを調査しない。
- 個別に許可されない限り、applicationの挙動、依存関係、directory構成、既存規約の文面を変更しない。
- 規約の提案と成果物は、規約文書、検証のみを行う強制手段、agent向け指示、それらのproject固有設定に限定する。product機能とruntimeまたはcontentの挙動は、提案や設計の段階でも規約の成果物に含めない。

## 現在のプロジェクトを監査する

依頼と統治文書から初期scopeを定める。監査範囲を広げる前に、repository、package、言語、生成code、infrastructureの境界を調べる。localで確認できず、対象となる規約項目または成果物を実質的に変える境界だけをユーザーへ確認する。

### 技術スタックを確認する

依頼された規約に影響する技術だけを特定する。

- 言語、framework、runtime、package manager、確認済みversion
- application、library、生成物、fixture、test、infrastructureの境界
- formatter、linter、type checker、test runner、build tool、editor設定
- 代表的なcodeで実際に使われるdirectoryとfileの命名pattern
- 現在の挙動を強制するCI checkとlocal command

証拠の確度を**確認済み**、**観測pattern**、**仮定**に分ける。繰り返されるpatternは観測済み慣行であり、自動的に規約とはならない。

### 既存の正本を探す

固定されたファイル名一覧だけに頼らず、プロジェクト固有の場所とtool設定を調べる。統治する各情報源について次を記録する。

- pathと適用範囲
- 規範文書、実行可能な設定、実装patternのどれか
- 優先順位と、ルートまたは下位指示との重複
- AIエージェントが変更前に読むよう指示されているか
- 記載された検証commandが存在し、該当範囲で動くか

文書、設定、CI、実装間の矛盾を事実として報告する。統治文書が適用可能な優先順位または矛盾解決手順を定義している場合はそれに従い、どちらもない場合は勝手に正しい側を選ばない。

## 監査済み項目を分類する

上記の監査完了後、scope内の規約項目ごとに確認済みの根拠から分類し、該当する最も安全な経路を使う。

1. **新規**：その項目を統治する実装や規約がまだ確立していない。
2. **規約ありの既存**：規範として記述された規約がその項目を統治しているか、実行可能な設定が統治文書で指定されている、project commandやCIから呼び出されている、または確認済みtoolchain、editor、language serverからその項目について既定で読み込まれる。
3. **規約なしの既存**：実装と構成は存在するが、その項目を統治する規範文書も有効な実行可能設定も存在しない。

設定fileは、対象toolとversionが影響範囲について明示的または既定で読み込むことを確認した場合だけ有効と扱う。それ以外は統治する正本ではなく追加調査が必要な証拠として扱う。混在するprojectでは未実装項目に**新規**、統治済み項目に**規約ありの既存**、実装済みだが未規定の項目だけに**規約なしの既存**を使う。proseがないことを理由に、有効な実行可能規約を存在しないものとして扱わない。

証拠が不十分な場合は確認対象と分類に必要な証拠を報告し、変更提案の前に焦点を絞った質問をする。特定のファイル名がないことだけを、規約が存在しない証拠にしない。

適切な経路や承認境界が不明な場合は[conversation-examples.md](references/conversation-examples.md)を読む。規約文書、`AGENTS.md`連携、最終報告を提案する前に[deliverables.md](references/deliverables.md)を読む。

## 現在の推奨事項を調査する

local監査の後、未解決または依頼された項目だけを調査する。

次の順序を使う。

1. 確認済みversionに対応する現在の公式推奨
2. 言語またはframeworkの標準と、保守されているfirst-party tool
3. 現在の証拠で裏付けられる、広く採用されたecosystem慣行
4. 既存projectとの適合性
5. teamによる明示的な選択

一次情報を優先する。source URLまたは文書、該当version、参照日を記録する。modelの記憶だけで規約を最新、公式、一般的と断定しない。公式推奨がない場合や複数の公式選択肢が有効な場合はその事実を示し、推奨理由を説明する。普及度は同等候補の判断材料であり、project適合性の代替ではない。

この根拠確認より前に、特定のtool、framework、package manager、layoutを推奨defaultとして挙げない。調査に追加情報が必要な場合は、未確認の選択肢を質問へ埋め込まず、productと運用の要件を尋ねる。

必要な現在のsourceへアクセスできない場合、影響する推奨の根拠を`Not checked`とする。最新、公式、一般的であることを未確認と明示し、確認済みのlocal evidenceだけで続けるか推奨を保留するか確認する。外部調査ができないことを、役に立つlocal監査まで停止する理由にしない。

考え得る全項目を調査しない。次から該当する項目だけを扱う。

- formatting、lint、type、import、言語構文、API境界
- directoryの所有、依存方向、fileとsymbolの命名
- test、fixture、生成file、document、comment
- error、log、configuration、environment variable、dependency方針
- securityの基本、editor整合性、build check、CIによる強制

projectの初期構築が範囲に含まれる場合は、別枠の該当するfoundation baselineとして、runtime固定とlockfile方針、ignore・改行・editor設定、必要なREADMEまたはcontribution guide、CI、依存更新とsecurity check、秘密情報の扱いを評価する。不足はコーディング規約ではなく任意の基盤提案として示し、項目ごとにfileを要求しない。

既存toolとnative機能を優先する。承認された規約を既存手段で十分に強制できない場合だけ依存関係を追加する。

## 分類に対応する経路を進む

### 新規

確認済みの言語またはframeworkごとに、小さな推奨baselineを提示する。公式の裏付け、projectへの影響、未解決の選択を説明する。次のまとまりを一つずつ決める。

1. stackとversion方針
2. 規約の正本と適用範囲
3. directoryと命名model
4. formatting、静的検査、test
5. agent向け指示とCIによる強制

承認前にfileを作成したり、toolをinstallしたり、directoryを作ったりしない。

### 規約ありの既存

AIエージェントが現在の規約を発見して従えるか評価する。正本、適用範囲、優先順位、統治文書からのlink、実行可能な強制手段を確認する。

既存の契約を維持する。ユーザーが改訂を明示的に依頼しない限り、次を守る。

- 既存規約の置換、改名、再編、書き換えを提案しない
- 別の選択が一般的という理由だけで、teamの選択を誤りと扱わない
- 既存の意味を変えない追加提案だけを提示する
- 推奨が既存規約と衝突する場合、衝突を報告して改訂案を希望するか確認し、この時点では改訂案を提示しない

既存の正本と検証commandを`AGENTS.md`から参照する追加は、規約の意味を変えない場合だけ追加提案として扱う。編集前に確認する。

ユーザーが改訂を明示的に許可した場合、通常の追加ではなく移行として扱う。現在の正本と変更先の規約を正確に特定し、既存code、設定、CI、文書、下位scopeへの影響を調べ、互換性と既存違反を報告し、rolloutと例外を合意し、提案と最終報告に根拠と理由を記録する。規約改訂の許可だけでは、code、依存関係、CIの変更まで許可されたことにならない。後述の変更gateで正確なpathへの承認を得る。

### 規約なしの既存

最小限の代表sampleからdraftを推定する。次を分ける。

- **推定済み慣行**：すでに一貫して存在するが、まだ正本ではないpattern
- **例外または曖昧さ**：判断が必要な競合pattern
- **外部推奨**：projectではまだ採用されていない現在の推奨

既存の文書階層を確認してから、既存構成を維持するproject固有の文書pathとoutlineを提案する。文書階層を確認できていない場合、pathは暫定と明記する。作成するか確認する。ユーザーが承認するまで推定した慣行を承認済みと表現せず、draftと整合させるためにcodeを再編しない。

## 判断と承認を得る

重要な判断ごとに、推奨、根拠、本当に有効な場合だけ代替案、それぞれの影響を示す。ユーザーが一括回答や選択の委任を希望しない限り、関連する判断を一組ずつ確認する。

各組の後、次の短いcheckpointを維持する。

- 確認済みのproject事実
- 推定済みだが未承認の慣行
- 承認済みの判断
- 承認待ちの追加提案
- 未解決の衝突またはblocker
- 現在の規約scope外として保留した発見事項

ファイル変更前に、作成または更新する正確なpath、各変更の目的、対象外file、予定する検証を示す。この提案への明示承認を得る。他の追加が承認済みでも、既存規約の変更には明示的な対象指定が必要である。

「OK」や「続けてください」のような短い返答は、直前に提示され承認待ちになっている正確な提案だけへの承認として扱う。正確な提案が承認待ちでない場合は、次に合意した規約の組へ戻るかユーザーへ確認し、保留事項や内部計画をscopeへ昇格させない。

## 規約を強制可能にする

機械検証できる挙動は実行可能な設定を正本とする。proseはarchitecture意図、toolで表現できない命名判断、例外、準拠を証明するcommandに使う。同じ規約を複数文書へ重複させない。

規約の強制とproduct実装を分ける。強制手段は不適合を検証または拒否してよいが、productが公開する内容やruntimeの挙動を追加または変更してはならない。route、loader、rendering、公開処理、runtime API、domain workflowは、記述済み規約が動機でもproduct作業として扱い、その作業が個別に依頼され承認されない限りgapを保留する。

既存projectへformatter、linter、type checker、test、必須CI checkを導入または厳格化する前に、自動修正を行わず現在の違反を把握する。適用範囲を合意し、既存違反を今回修正する、確認済みbaselineを採用する、変更fileだけを検査する、文書化した一時除外から段階導入する、のいずれかを明示的に選ぶ。checkをCIで必須にする時点を示す。rolloutの承認前にrepository全体を自動修正したり、失敗すると分かっているcheckを必須化したりしない。

`AGENTS.md`または同等の統治文書と連携するときは、次を示す最小限のproject固有の追記にする。

- 規約の正本path
- 適用範囲
- 確立済みの優先順位
- agentが読む時点
- 影響範囲に対する正確な検証command

下位のinstruction fileを考慮する。ルートの参照は、より具体的な統治文書を上書きしない。文書が存在するだけでagentの遵守を保証したと主張しない。

## 検証して終了する

承認されたproject固有のcheckだけを実行する。参照pathとcommandが存在すること、tool設定と文書の契約が一致すること、下位scopeが一貫していること、未承認の規約が変更されていないことを確認する。新規導入または厳格化したcheckでは、合意済みbaseline違反と新規regressionを区別し、承認されたrollout状態が成功するまで導入完了と報告しない。

[deliverables.md](references/deliverables.md)を読み、その**Final report**契約に従う。

許可された境界で終了する。監査の完了は実装の許可ではない。
